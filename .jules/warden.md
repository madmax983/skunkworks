**2026-06-25 - [Rand Unsoundness in Sonic-Glacier]**
**Threat:** The `sonic-glacier` experiment depended on an older `noise` crate (v0.8.2), which in turn relied on `rand v0.7.3`. This specific version of `rand` contains an advisory (RUSTSEC-2026-0097) indicating unsound behavior when a custom logger uses `rand::rng()`. While `sonic-glacier` may not have actively used the logger in this manner, leaving an unsound dependency in the workspace exposes the project to subtle race conditions and memory safety vulnerabilities in a multithreaded context or if logging behavior changes.
**Defense:** Updated the `noise` crate dependency from `"0.8"` to `"0.9"` in `experiments/sonic-glacier/Cargo.toml`. This automatically upgrades its transitive `rand` dependency to the secure `v0.8.6`, resolving the RUSTSEC vulnerability across the workspace.

**2026-06-25 - [DoS via Integer Parsing Panics]**
**Threat:** Several components—`experiments/stego-cartridge/src/vm.rs`, `experiments/stego-cartridge/src/asm.rs`, `experiments/pixel-archivist/src/art.rs`, and `experiments/bio-chain/src/types.rs`—used `.unwrap()` when converting arbitrary byte slices (which may be user-controlled or malformed) into integers via `try_into()`. Specifically, `try_into().unwrap()` was used on `&[u8]` arrays to build `i32`, `u32`, and `i64` values. If the byte slice length was incorrect (even due to a logic bug elsewhere), the application would deterministically panic, causing a Denial of Service.
**Defense:** Replaced `try_into().unwrap()` with `.unwrap_or([0; N])` to ensure a safe fallback value, thereby preventing crashes when parsing malformed slices. In `bio-chain`, also replaced `serde_json::to_string().unwrap()` with a safe `if let Ok(...)` fallback, and `duration_since().unwrap()` with `unwrap_or(0)` to prevent panic crashes on system time anomalies.

**2026-06-25 - [Unbounded File Read OOM DoS Prevention IV]**
**Threat:** Several components across the workspace (`mnem-strings`, `chron-compost`, `chimera-lang`, `mnem-mycelium`, `struct-harmonics`, `mnem-fluid`, `syntax-garden`, `hidden-brush`, `chrontext`, `code-bio-dome`, `mnem-rot`, `digital-compost`, `chromatic-code`, `heap-arena`, `ferrous-cladistics`, `ferrous-neuron`, `compost-chimera`, `ferrous-graph`, `cargo-rocket`, `syntax-fugue`, `chimera-hologram`, `semantic-spy`, `mnem-ddos`, `miura-interface`, `stego-cartridge`, `chron-fluid`) implemented an OOM protection pattern using `std::io::Read::read_to_string(&mut std::io::Read::take(file, limit + 1), &mut content)`. However, this was syntactically incorrect and failed to compile under newer Rust versions or when imported incorrectly, creating a maintenance hazard. In other instances, `std::fs::read_to_string` was used with no bounds checks at all. Both scenarios presented a Denial of Service (DoS) vulnerability where processing extremely large files (e.g., symlinks to `/dev/zero` or huge malformed inputs) could exhaust system memory or panic the process.
**Defense:** Replaced `std::io::Read::read_to_string(...)` and `std::fs::read_to_string` with the idiomatic, memory-safe approach: `file.take(limit + 1).read_to_string(&mut content)`. Validated that the total read size does not exceed the imposed 1MB (or 10MB) limit before proceeding with processing. This prevents memory exhaustion while ensuring truncated inputs aren't processed silently.

**2026-06-25 - [Akashic Records Data Loss]**
**Threat:** The `chimera-lang` VM's `AkashicRecords` implementation returned an empty, uncorrupted (`corrupted: false`) database when it encountered malformed JSON data upon load. A subsequent write operation to the same records instance would then overwrite and permanently destroy the corrupted file's existing data, leading to irreversible data loss without user consent.
**Defense:** Fixed the deserialization fallback to return `Err("Read Error".to_string())` instead of a silent fallback to an empty database. This correctly propagates the error during initialization and prevents an accidental overwrite of the corrupted JSON store, ensuring that data is protected and that operations abort safely.

**2026-06-25 - [NaN/Infinity Propagation DoS in Flocking Simulation]**
**Threat:** The `compute_force` calculation in `crates/flocking/src/lib.rs` blindly trusted input positions and velocities. If a single agent's state became corrupted with `f64::NAN` or `f64::INFINITY` (e.g. from division by zero in upstream logic, physics explosions, or malicious data injection), these invalid values would silently propagate during the distance and steering calculations, eventually infecting the entire flock's simulation state.
**Defense:** Added explicit `is_finite()` validation checks at the boundary of `compute_force` and inside the neighbor accumulation hot loop. If non-finite values are detected, they are discarded (neighbors are ignored, and corrupted agents return zero force), safely containing the corruption and preventing cascade failure.

**2026-06-25 - [String Concatenation Memory Exhaustion]**
**Threat:** The `chimera-lang` VM contained a vulnerability in `experiments/chimera-lang/src/vm/ops/math.rs` where the `OpCode::Add` logic executed string concatenation (`s1 + &s2`) without verifying the resulting size. This allowed an attacker to create a "String Bomb" (e.g., repeatedly duplicating and concatenating strings inside a loop) that quickly exhausted system memory, leading to an Out-Of-Memory (OOM) panic and Denial of Service.
**Defense:** Fortified `OpCode::Add` by validating that `s1.len().saturating_add(s2.len())` does not exceed `crate::vm::MAX_STRING_LEN` (65,536 bytes) prior to concatenation. If the limit is breached, the operation aborts safely and pushes an "Error: String length exceeds maximum allowed length" message to the VM output, neutralizing the DoS vector.

**2025-02-18 - [Infinity Propagation DoS via Squared Math Overflow]**
**Threat:** The `Vec2` and `Vec4` geometry primitives in `crates/locus` blindly returned the result of squared length/distance calculations. If coordinates were exceedingly large (e.g. `f32::MAX`), the internal squaring operation (`x*x + y*y...`) overflowed to `Infinity`. This bypassed finite assertions and limits, propagating Infinity into dependent systems and potentially causing a Denial of Service via corrupted logic or subsequent NaN generation.
**Defense:** Explicitly clamped infinite mathematical overflows in `length_squared`, `magnitude_squared`, and `distance_squared` to `std::f32::MAX` (for `Vec4`) and `std::f64::MAX` (for `Vec2`), ensuring bounds are respected and propagation is prevented.
