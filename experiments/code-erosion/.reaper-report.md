# Forensic Report: code-erosion

**Case ID:** 2026-CODE-EROSION-01
**Status:** CONDEMNED
**Grace Period Ends:** +24 Hours

## Observed Failure Modes
- **Documentation Void:** `README.md` is absent. The purpose and mechanics of the experiment are opaque to the swarm.
- **Concept Failure:** The specimen claims to be "code erosion" but implements a trivial mapping of Git commit hashes to random coordinates. The erosion simulation, while functional, operates on this random noise rather than meaningful code metrics.
- **Redundancy:** The "data-to-terrain" metaphor is crowded (`tectonic-git`, `log-landscape`). This specimen adds no unique evolutionary traits.

## Forensic Analysis
The specimen `code-erosion` exhibits a classic disconnect between title and implementation.

*   **Code Quality:** The `terrain.rs` module contains a decent hydraulic erosion implementation (droplets, sediment capacity). However, `git.rs` uses `DefaultHasher` to map file paths to grid coordinates `(hash % width, hash / width)`. This results in white noise, not a structured landscape derived from the codebase structure.
*   **Staleness:** Lack of documentation and simple implementation suggests abandonment.
*   **Persona Alignment:** Generic. It lacks the "obsessive" quality of a true Alchemist or Topologist experiment. It feels like a tech demo for `terrain.rs` with a thin Git wrapper.

## Verdict
**CONDEMN.**
The specimen is a "zombie" experiment—technically functional code that fails to live. It consumes space without generating insight.

## Requirements for Salvation
1.  **Documentation:** Create `README.md` explaining the erosion model and how it relates to the code.
2.  **Meaningful Mapping:** Replace the random hash mapping with semantic mapping (e.g., directory depth = elevation, file size = initial height, commit age = rock hardness).
3.  **Visual Feedback:** The TUI should indicate *what* code is being eroded. "File X was washed away" is more interesting than "Pixel (10,10) decreased by 0.1".
